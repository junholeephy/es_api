# 성능 테스트 지침

**단위(Unit)**: `es-crawler`
**작성일**: 2026-09-09

---

## 1. 성능 요구사항

명시적 SLA 는 **없습니다** (NFR-P05). 무인 배치로 하루 한 번 19:00 에 돌고,
다음 실행까지 24시간이 있습니다.

대신 확인해야 하는 것은 두 가지입니다.

| 항목 | 기준 | 근거 |
|---|---|---|
| **메모리가 데이터 양에 따라 늘지 않는가** | 문서 수와 무관하게 일정 | NFR-P04, NFR-P05 |
| **하루치가 24시간 안에 끝나는가** | 여유롭게 통과해야 함 | 다음 실행과 겹치면 안 됨 |

예상 규모는 하루 **10만 ~ 100만 건**입니다 (NFR-P01, 추정값).

## 2. 이미 측정된 값 (2026-09-09, 개발 장비)

### 2.1 변환 단계 — 순수 스트리밍 경로

500,000 문서 / 90 MB JSONL 을 CSV 로 변환:

| 항목 | 값 |
|---|---|
| 소요 시간 | **1.9초** |
| 최대 RSS | **45.6 MB** |
| 처리율 | 약 260,000 행/초 |

```bash
/usr/bin/time -l .venv/bin/python src/run.py --config <설정> --only convert \
    --from 2026-09-08T18:00 --to 2026-09-09T18:00
```

**메모리가 입력 크기와 무관합니다.** 90 MB 파일을 45 MB 로 처리했습니다 —
파일 전체를 올리지 않고 한 줄씩 흘려보낸다는 뜻입니다 (NFR-P04 충족).

### 2.2 `--dry-run` 측정값의 주의점

| 문서 수 | 소요 | 최대 RSS |
|---|---|---|
| 10,000 | < 0.1초 | 57 MB |
| 100,000 | 0.4초 | 135 MB |

**이 메모리 증가는 파이프라인이 아니라 테스트 장치 때문입니다.**
`synth.generate(n)` 이 가짜 문서 n개를 **리스트로 먼저 만든 뒤** 넘기므로,
그 리스트 자체가 메모리를 차지합니다. 실제 실행에서는 Elasticsearch 가
배치 단위로 흘려보내므로 이런 증가가 없습니다.

따라서 **`--dry-run` 의 peak 값으로 실제 메모리를 추정하면 안 됩니다.**
스트리밍 특성은 2.1 의 변환 단계 측정으로 확인합니다.

## 3. 추출 단계 측정 (실제 클러스터 필요)

추출은 대부분의 시간을 네트워크와 서버에서 보내므로, 개발 장비에서는 의미 있는
숫자가 나오지 않습니다. **실제 클러스터에서 첫 실행 때 측정합니다.**

```bash
/usr/bin/time -l python src/run.py --config configs/env.yaml
```

RUN SUMMARY 의 마지막 두 줄을 기록합니다.

```
extract   : 152,431 docs -> 1 jsonl
runtime   : 412.3s, peak 0.31GB
```

### 기록할 것

| 항목 | 어디서 |
|---|---|
| 하루치 실제 문서 수 | `extract` 줄 |
| 총 소요 시간 | `runtime` 줄 |
| 최대 메모리 | `runtime` 줄의 `peak` |
| JSONL 파일 크기 | `ls -lh outputs/*.jsonl` |
| scroll 왕복 횟수 (추정) | 문서 수 ÷ `batch_size` |

## 4. `batch_size` 조정

기본값 **2000** 은 100만 건 기준 scroll 500회를 가정한 것입니다 (NFR-P02).
실측 후 조정합니다.

```bash
# 배치 크기를 바꿔가며 같은 구간을 재실행
for size in 500 1000 2000 5000; do
  sed -i.bak "s/batch_size: .*/batch_size: $size/" configs/env.yaml
  rm -f outputs/.checkpoint.json outputs/*.jsonl
  echo "--- batch_size=$size ---"
  python src/run.py --config configs/env.yaml --only extract 2>/dev/null | grep -E "runtime|extract"
done
```

### 판단 기준

| 관찰 | 조치 |
|---|---|
| 배치를 키워도 시간이 줄지 않음 | 병목이 네트워크가 아니라 서버 쪽. 그대로 둔다 |
| 배치를 키우니 메모리가 눈에 띄게 늘어남 | 한 응답이 커진 것. 되돌린다 |
| 서버에서 `circuit_breaking_exception` | **즉시 낮춘다.** 클러스터에 부담을 준 것이다 |
| 배치를 줄이니 시간이 크게 늘어남 | 왕복 비용이 지배적. 다시 키운다 |

**클러스터 부하를 줄이려고 구간을 쪼갠 것이므로, 속도를 위해 부하를 키우는 조정은
목적에 반합니다.** 시간이 24시간 안에 들어오면 그것으로 충분합니다.

## 5. 구간 크기 조정

하루치가 너무 오래 걸리거나 클러스터에 부담이 되면 `chunk_hours` 를 낮춥니다.

```yaml
chunk:
  chunk_hours: 6      # 하루를 네 조각으로
```

| 효과 | 내용 |
|---|---|
| 한 번의 조회가 다루는 문서 수 감소 | 서버 부하 분산 |
| 파일이 구간 수만큼 생김 | 파일명에 시각이 들어가므로 충돌 없음 |
| 총 소요 시간은 비슷하거나 약간 증가 | 조회 준비 비용이 구간마다 든다 |
| 중단 시 잃는 작업량 감소 | 재개 단위가 작아진다 |

**24를 넘길 수 없습니다.** 넘기면 시작하지 않습니다 (BR-C01).

## 6. 회귀 확인

성능 관련 코드를 고친 뒤 스트리밍 특성이 깨지지 않았는지 확인합니다.

```bash
# 50만 행짜리 JSONL 을 만들어 변환 단계만 측정
TMP=$(mktemp -d)
.venv/bin/python - "$TMP" <<'PY'
import json, sys
from pathlib import Path
out = Path(sys.argv[1]) / "data-2026-09-09T180000+0900.jsonl"
with open(out, "w", encoding="utf-8") as f:
    for i in range(500_000):
        f.write(json.dumps({"_index": "x", "_id": f"{i:09d}", "_score": None,
                            "_source": {"@timestamp": "2026-09-09T10:00:00Z",
                                        "user": {"name": "abc"}}}) + "\n")
PY
# 설정의 output.directory 를 $TMP 로 두고
/usr/bin/time -l .venv/bin/python src/run.py --config <설정> --only convert \
    --from 2026-09-08T18:00 --to 2026-09-09T18:00 2>&1 | grep -E "convert |maximum resident"
rm -rf "$TMP"
```

**기준선**: 약 2초, 최대 RSS 50 MB 이하.
**RSS 가 입력 크기를 따라 늘어나면 스트리밍이 깨진 것입니다** — 어딘가에서
`list(...)` 로 전부 모으고 있다는 뜻이며, 100만 건에서 메모리가 터집니다.

## 7. 측정하지 않는 것

| 항목 | 왜 |
|---|---|
| 동시 사용자 / 처리율(RPS) | 서버가 아니다. 하루 한 번 도는 배치다 |
| 응답 시간 백분위 | 대화형 요청이 없다 |
| 부하 테스트 도구 (JMeter, k6) | 우리가 부하를 **주는** 쪽이며, 그 부하는 구간 분할로 이미 제한된다 |
| 스트레스 테스트 | 한계까지 밀어붙이면 클러스터가 다치고, 그건 이 도구의 목적과 정반대다 |
| 확장성 | 순차 실행이 확정이다. 늘릴 축이 없다 |
