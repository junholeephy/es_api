## Question 1 — 스키마 검증의 범위
NFR 단계에서 "청크마다 앞 1000건 표본"으로 적응하기로 했습니다.
그런데 RUN SUMMARY의 `schema` 줄은 **한 줄**입니다. 여러 청크를 돌 때 어떻게 합칠까요?

A) **첫 청크만 검증** — 표본 1000건을 첫 청크에서만 뽑음. 가장 싸고, 포맷은 하루 사이에
   잘 바뀌지 않는다는 가정

B) **매 청크 표본 검증 후 합집합** — 청크마다 1000건씩 보고 위반을 합쳐서 한 줄로.
   5일치를 돌면 5000건을 보게 되어 놓칠 확률이 낮아짐

C) **매 청크 전수 검증** — 스트리밍 중 모든 문서를 검사. 가장 정확하지만
   100만 건 기준으로 처리 시간이 늘어남

X) Other (아래 [Answer]: 뒤에 직접 설명해 주세요)

[Answer]: A

## Question 2 — JSONL은 있는데 체크포인트에 기록이 없을 때
체크포인트 파일을 실수로 지웠거나, 다른 경로에서 실행했던 경우입니다.
`data-2026-09-09T180000+0900.jsonl` 은 있는데 `.checkpoint.json` 에는 그 키가 없습니다.

A) **다시 추출해서 덮어씀** — 체크포인트가 유일한 진실. 파일이 있어도 신뢰하지 않음.
   안전하지만 클러스터에 부하를 다시 줌

B) **건너뛰고 체크포인트만 보정** — 파일이 있으면 완료로 간주하고 `done` 기록을 채워 넣음.
   재추출 비용이 없지만, **쓰다 만 파일이었다면 불완전한 데이터를 완료로 확정**함

C) **경고 후 중단** — 사람이 판단하도록 멈춤. `--force` 같은 인자로만 진행

X) Other (아래 [Answer]: 뒤에 직접 설명해 주세요)

## Question 3 — 일부 청크가 실패했을 때 CSV 변환을 할까요? ⚠️
규약 우선 적용으로 추출과 변환이 **한 번 실행 안에서** 이어집니다.
기존 D-4의 `extract && convert` 는 추출이 실패하면 변환을 아예 하지 않는다는 뜻이었는데,
단일 실행에서는 그 의미를 다시 정해야 합니다.

예: 5일치를 요청했는데 3일은 성공, 2일은 실패했습니다.

A) **성공한 청크만 변환** — 3일치 CSV가 나옴. 실패한 2일은 다음 실행에서 재시도되어
   그때 CSV까지 생성됨. 종료 코드는 `1`

B) **하나라도 실패하면 변환 안 함** — 기존 `&&` 의미를 그대로 재현.
   JSONL만 남고 CSV는 없음. 다음 실행에서 전부 정리됨. 종료 코드는 `1`

C) **전부 변환 시도** — 이미 디스크에 있는 JSONL은 이전 실행 것이라도 모두 변환

X) Other (아래 [Answer]: 뒤에 직접 설명해 주세요)

[Answer]: A

## Question 4 — RUN SUMMARY 의 `status` 값
규약은 종료 코드 `1` 을 "돌았지만 온전치 않다"로 정의합니다.
이 프로젝트에서 `1` 이 되는 원인은 **두 가지**입니다 — 스키마 위반, 그리고 청크 실패.
`status` 줄에 이를 어떻게 표현할까요?

A) **원인을 구분해 표기** — `OK` / `SCHEMA MISMATCH` / `CHUNKS FAILED` / `SCHEMA MISMATCH + CHUNKS FAILED`.
   화면만 보고 무엇이 문제인지 알 수 있음

B) **규약 예시대로 단순하게** — `OK` / `CONTRACT MISMATCH`.
   상세는 위쪽 `schema` · `chunks` 줄에 이미 있으므로 중복을 피함

X) Other (아래 [Answer]: 뒤에 직접 설명해 주세요)

[Answer]: A

## Question 5 — 진행 상황 로깅 빈도 (stderr)
100만 건이면 배치 크기 2000 기준 scroll 500회입니다. 무엇을 얼마나 찍을까요?

A) **청크 단위만** — 청크 시작/종료에 한 줄씩. 하루 1청크면 실행당 2줄.
   조용하지만 긴 청크에서 진행 중인지 알 수 없음

B) **청크 단위 + N건마다 진행률** — 예: 5만 건마다 `... 50,000 docs` 한 줄.
   100만 건이면 20줄. 살아있는지 확인 가능

C) **scroll 배치마다** — 500줄. 너무 많음

X) Other (아래 [Answer]: 뒤에 직접 설명해 주세요)

[Answer]: B

## Question 6 — 체크포인트 내구성
`os.replace` 는 원자적이지만, `fsync` 없이는 OS 버퍼에만 있는 상태에서
전원이 끊기면 파일이 비어 있을 수 있습니다.

A) **`fsync` 후 `replace`** — 청크마다 한 번이라 비용이 무시할 수준이고,
   갑작스러운 종료에도 상태가 남음

B) **`replace` 만** — 프로세스 크래시에는 안전하고, 전원 차단은 이 도구의 위협 모델 밖.
   코드가 더 단순함

X) Other (아래 [Answer]: 뒤에 직접 설명해 주세요)

[Answer]: A
