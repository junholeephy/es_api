## 2. 시스템 개요

```
+---------------------+
|  CLI / Scheduler    |   external scheduler calls CLI daily at 19:00 KST
|  (--from / --to)    |
+---------------------+
           |
           v
+---------------------+
|  Date Chunker       |   period -> list of daily chunks
|  (max 24h / chunk)  |   refuses a chunk size over 24h
+---------------------+
           |
           v
+---------------------+       +---------------------+
|  Checkpoint Store   | <---> |  Extractor          |
|  (state file)       |       |  elasticsearch-py   |
|  done / failed      |       |  scroll API         |
+---------------------+       +---------------------+
                                         |
                                         v
                              +---------------------+
                              |  JSONL Writer       |
                              |  one file per day   |
                              |  raw ES hits kept   |
                              +---------------------+
                                         |
                                         v
                              +---------------------+
                              |  CSV Converter      |
                              |  selected columns   |
                              |  header renaming    |
                              +---------------------+
                                         |
                                         v
                                data-YYYY-MM-DD.csv
```

**텍스트 대안**: CLI 또는 스케줄러가 시작일·종료일을 받아 Date Chunker에 넘긴다. Chunker는 기간을 하루 단위 청크로 나눈다. 각 청크마다 Checkpoint Store를 확인해 이미 완료된 청크는 건너뛰고, 남은 청크를 Extractor가 scroll API로 순차 추출한다. 결과는 하루당 JSONL 파일 하나로 디스크에 저장된다. 이후 CSV Converter가 JSONL을 읽어 설정된 컬럼만 골라내고 헤더명을 바꿔 CSV로 저장한다.

## 3. 기능 요구사항 (Functional Requirements)

### FR-1: Elasticsearch 연결
- 공식 **`elasticsearch-py` 8.x** 클라이언트로 Elasticsearch **8.15.3** 서버에 접속한다.
- 인증은 **API Key** 방식을 사용한다.
- 접속 정보(호스트 URL, API Key)는 **`.env` 파일**에서 읽는다.
- 시작 시 연결 및 인증 실패는 즉시 명확한 오류로 알린다.

### FR-2: 날짜 범위 분할 (Date Chunking)
- 시작일·종료일을 입력받아 **하루 단위 청크 목록**으로 자동 분할한다.
- 예: 5일 범위 → 5개 청크로 나눠 **순차 실행**한다.
- **개별 청크 하나의 시간 폭은 24시간을 초과할 수 없다.** 전체 요청 기간에는 상한이 없다.
- **하루의 경계는 자정이 아니라 설정 가능한 기준 시각(anchor)이다. 기본값 18:00 KST.**
  즉 하나의 청크는 `[D-1 18:00, D 18:00)` (KST) 형태의 24시간 반개구간이다.
- 청크 크기는 설정으로 더 작게(예: 6시간) 지정할 수 있다.
- 청크 크기가 24시간을 초과하도록 설정되면 **경고를 출력하고 실행하지 않는다**.
- 청크 경계는 반개구간 `[start, end)` 으로 정의해 인접 청크 간 **누락도 중복도 없게** 한다.

### FR-3: 데이터 추출 (Scroll 기반)
- 각 청크에 대해 시간 필드 범위 쿼리를 만들어 Elasticsearch에 조회한다.
- 결과가 `index.max_result_window`(기본 10,000)를 초과할 수 있으므로 **scroll API**로 전체를 페이징한다.
- 배치 크기(`size`)와 scroll 유지 시간(`scroll` TTL)은 설정 가능하다.
- **청크 처리가 끝나면 반드시 scroll 컨텍스트를 정리**한다(정상 종료·예외 발생 모두).
- 결과를 전부 메모리에 적재하지 않고 **스트리밍으로 순차 처리**한다.

### FR-4: JSONL 저장
- 추출한 문서를 **JSON Lines(`.jsonl`)** 파일로 디스크에 저장한다 (한 줄에 문서 하나).
- **하루당 파일 1개**로 분리한다 (예: `data-2026-09-09.jsonl`).
- 파일명의 날짜는 **해당 창(window)의 종료 날짜**를 쓴다.
  예: `[2026-09-08 18:00 KST, 2026-09-09 18:00 KST)` → `data-2026-09-09.jsonl`
- Elasticsearch 원본을 보존해, 재추출 없이 변환 단계만 다시 실행할 수 있게 한다.

### FR-5: CSV 변환
- 저장된 JSONL을 읽어 **CSV**로 변환한다. 추출과 분리된 별도 단계로 실행 가능해야 한다.
- **설정 파일에 지정한 컬럼 목록만** 추출한다 (전체 필드 평탄화는 하지 않는다).
- 컬럼 지정은 중첩 필드를 점 표기법으로 가리킬 수 있다 (예: `user.name`).
- **CSV 헤더명을 원본 필드명과 다르게 지정**할 수 있다 (필드 → 헤더명 매핑).
- 지정한 필드가 문서에 없는 경우의 처리 방식(빈 값)을 일관되게 적용한다.

### FR-6: 체크포인트 및 재개
- 청크별 진행 상태(대기/완료/실패)를 **상태 파일**에 기록한다.
- 중단 후 재실행하면 **완료된 청크는 건너뛰고 실패·미처리 청크부터 이어서** 실행한다.
- 같은 날짜를 다시 실행해도 결과가 동일하도록(idempotent) 동작한다.

### FR-7: 설정
다음 항목을 설정 파일 및/또는 CLI 인자로 지정한다.

| 항목 | 예시 |
|---|---|
| 대상 인덱스 | `logs-*` |
| 시간 필드명 | `@timestamp` |
| 추가 쿼리 필터 | 특정 필드 값 조건 |
| 추출 컬럼 목록 + 헤더명 매핑 | `user.name` → `사용자명` |
| 청크 크기 | 기본 24시간 |
| 배치 크기 / scroll TTL | `1000` / `5m` |
| 출력 디렉터리 | `./output` |

시크릿(API Key, 호스트)은 설정 파일이 아니라 **`.env`** 에 둔다.

### FR-8: 실행 인터페이스
- 핵심 로직은 **재사용 가능한 Python 패키지**로 구성한다 (`import` 해서 사용 가능).
- 그 위에 **얇은 CLI 진입점**을 제공한다 (예: `python -m es_crawler --from 2026-09-01 --to 2026-09-05`).
- CLI는 외부 스케줄링 도구(cron 등)가 호출하기 적합해야 한다.

### FR-9: 일일 스케줄 실행 지원
- 외부 스케줄러가 **매일 19:00 KST에 하루치를 가져오는** 사용 방식을 지원한다.
- **날짜 인자 없이 호출하면 `[전날 18:00 KST, 당일 18:00 KST)` 창을 추출한다.**
  19:00에 실행하므로 창의 끝(18:00)이 이미 지나 있어, 데이터가 잘리지 않는다.
- 종료 코드로 성공/실패를 구분해, 스케줄러가 실패를 감지할 수 있게 한다.

### FR-10: 로깅
- 청크별 진행 상황, 추출 문서 수, 소요 시간, 오류를 로그로 남긴다.
- 스케줄러가 무인 실행하므로, 로그만 보고 무엇이 실패했는지 판단할 수 있어야 한다.

## 4. 비기능 요구사항 (Non-Functional Requirements)

### NFR-1: 기술 스택
- **Python** (pip + venv)
- **`elasticsearch` 8.x** (서버 8.15.3과 메이저 버전 정합)
- 테스트: **pytest** + **hypothesis** (속성 기반 테스트)

### NFR-2: 코드 품질
- 공개 함수·클래스에 **타입 힌트**를 붙인다.
- 산출물 수준: 실제로 반복 사용할 수 있는 수준 (Q11=B).
- 불필요한 추상화와 아직 필요 없는 확장성 설계는 지양한다 (YAGNI).

### NFR-3: 테스트 (PBT 부분 적용)
- 예제 기반 테스트(pytest)와 속성 기반 테스트(hypothesis)를 함께 둔다.
- **속성 기반 테스트 대상** (Partial 모드: PBT-02, PBT-03, PBT-07, PBT-08, PBT-09만 blocking):
  - **왕복 (PBT-02)**: 문서 → JSONL 직렬화 → 역직렬화 = 원본
  - **불변식 (PBT-03)**: 날짜 분할 — 청크들의 합집합이 원래 기간과 같고, 겹치지 않으며, 모든 청크가 24시간 이하
  - **불변식 (PBT-03)**: JSONL → CSV — 출력 행 수 = 입력 문서 수, 컬럼 = 설정된 컬럼 목록
  - **제너레이터 품질 (PBT-07)**: ES 문서·날짜 범위에 대한 도메인 제너레이터를 재사용 가능한 형태로 정의
  - **재현성 (PBT-08)**: 실패 시 시드 로깅, shrinking 비활성화 금지
- PBT는 예제 기반 테스트를 대체하지 않는다.

### NFR-4: 오류 처리 및 재시도
- 일시적 오류(429 Too Many Requests, 502/503, 연결 타임아웃)는 **클라이언트 레벨 재시도**로 흡수한다.
- 재시도로 회복되지 않은 실패만 체크포인트에 "실패"로 기록한다.
- 청크 하나의 실패가 나머지 청크 실행을 막지 않는다 (기록 후 계속 진행, 마지막에 실패 요약).

### NFR-5: 메모리
- 대용량 결과를 전부 메모리에 올리지 않는다. 추출·저장·변환 모두 **스트리밍 처리**.

### NFR-6: 시크릿 관리
- API Key와 호스트 정보는 **`.env`** 로만 주입한다.
- `.env`는 버전 관리에서 제외하고(`.gitignore`), `.env.example` 템플릿을 제공한다.
- 로그에 API Key를 출력하지 않는다.

### NFR-7: 클러스터 부하
- 청크를 **순차 실행**한다 (병렬 실행 없음).
- scroll 컨텍스트를 확실히 정리해 서버 메모리에 검색 컨텍스트가 누적되지 않게 한다.

## 5. 제약 조건 (Constraints)

| ID | 제약 |
|---|---|
| C-1 | Elasticsearch 서버 버전 **8.15.3** 고정 |
| C-2 | **scroll API 사용** — ES 8.x에서 deprecated이나 사용자가 명시적으로 선택함 (아래 참고) |
| C-3 | **1회 조회(청크)의 시간 범위는 최대 24시간** — 클러스터 부하 감소를 위한 자체 규칙 |
| C-4 | `index.max_result_window` 기본값 10,000 — 이를 넘는 결과는 scroll로 페이징 |
| C-5 | 순차 실행 (병렬 없음) |

### C-2 참고: scroll API deprecation
Elasticsearch 8.x에서 scroll API는 deprecated 상태이며, 공식 권장은 `search_after` + PIT입니다.
scroll은 요청마다 검색 컨텍스트를 서버 메모리에 유지합니다.
**8.15.3에서 정상 동작하며**, 사용자가 Q4에서 A(scroll 사용)를 명시적으로 선택했습니다.
이 선택에 따라 **FR-3의 scroll 컨텍스트 정리 요구사항이 특히 중요**합니다 —
하루 단위로 반복 실행하는 구조에서 정리를 누락하면 C-3의 목적(부하 감소)과 정반대의 결과가 됩니다.

## 7. 확정된 설계 결정 (Resolved Decisions)

Requirements 검토 단계에서 사용자가 확정한 사항입니다.

### D-1: 실행 시각과 추출 창 (기존 가정 A-1을 사용자가 수정)
- 스케줄러는 **매일 19:00 KST**에 실행한다.
- 추출 대상은 **전날 18:00 KST ~ 당일 18:00 KST** 이다.
- 이 창은 정확히 24시간이므로 제약 **C-3(청크당 최대 24시간)을 만족**한다.
- 실행 시각(19:00)이 창의 끝(18:00)보다 1시간 뒤이므로, 색인 지연을 감안한 여유가 확보된다.

**파생 결정**: 하루의 경계가 자정이 아니라 18:00이므로, 청크 분할도 자정이 아닌
**설정 가능한 기준 시각(anchor, 기본 18:00 KST)** 에 정렬된다. 출력 파일명은 창의 **종료 날짜**를 쓴다.

### D-2: 타임존 (기존 가정 A-2를 사용자가 승인)
- 타임존은 설정 가능하며 **기본값은 `Asia/Seoul`(KST)** 이다.
- "하루"의 경계는 KST 기준으로 계산하고, Elasticsearch range 쿼리를 만들 때 **UTC로 변환**한다.
- KST 18:00 = UTC 09:00 이므로, 실제 쿼리는 `[D-1 09:00Z, D 09:00Z)` 형태가 된다.
